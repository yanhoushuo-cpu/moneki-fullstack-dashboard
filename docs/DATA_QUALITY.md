# 数据质量与清洗决策

本文件描述导入规则版本 `2026-08-19.1`。目标不是让数据“看起来干净”，而是保证每个进入经营指标的销售行都有可靠日期、外键、数量和金额，并且每个被排除的行可以回到原始 CSV 行号。

## 守恒关系

```text
原始行 12,131
- 完全重复副本 76
= 去重后唯一行 12,055

有效行 11,944
+ 唯一隔离行 111
= 去重后唯一行 12,055
```

金额缺失原始共有 120 行，其中 119 行满足安全补全条件并进入有效数据，剩余 1 行记录为 `missing_amount` 并隔离。

## 处理顺序

1. 按 UTF-8 读取三张 CSV，将销售原始字段和行号写入 `raw_sales`。
2. 使用销售表七个原始字段判定完全重复，保留第一次出现。
3. 日期、标识符、数量、金额和支付方式分别规范化。
4. 加载门店与商品维表，验证外键。
5. 仅在条件充分时补全缺失金额。
6. 收集一行的全部原因；有任何未解决原因则只写一条 `quarantined_sales`。
7. 通过全部规则的行写入 `sales`，金额以整数分保存。
8. 临时数据库完整提交后通过 `os.replace` 原子替换目标文件，失败不会留下半个数据库。

## 规范化规则

| 字段 | 输入差异 | 规范结果 |
|---|---|---|
| 日期 | `YYYY-MM-DD`、`DD-MM-YYYY`、`YYYY/MM/DD` | ISO `YYYY-MM-DD` |
| store_id / product_id | 前后空格、大小写不一 | `strip().upper()` |
| 金额 / 单价 | `¥`、逗号、空格、小数 | Decimal 解析后转整数分 |
| 数量 | 字符串整数 | 有符号整数 |
| 文本 | 前后空格 | 去除外部空白，不猜测内部内容 |

`s01` 必须规范为 `S01`。若只 trim 不 uppercase，会把 9 行合法记录误报为未知门店；这一边界有自动化测试。

## 修复与隔离

### 允许自动修复

- **完全重复记录**：七个销售字段全部相同才去重，不用订单号单独去重，因为一个订单可以包含多个商品行。
- **缺失金额**：商品外键存在、数量为正、维表单价有效时，用 `qty × unit_price` 补全，并记录 `amount_source=imputed`。

### 必须隔离

| 原因码 | 原因出现次数 | 决策 |
|---|---:|---|
| `quantity_amount_sign_conflict` | 63 | 数量和金额符号矛盾，不能擅自解释为退款 |
| `unknown_product` | 30 | 无法可靠 JOIN 商品名、品类和单价 |
| `unknown_store` | 7 | 无法可靠 JOIN 门店名、品类和地区 |
| `zero_quantity_nonzero_amount` | 11 | 零数量却有金额，业务含义不明确 |
| `missing_amount` | 1 | 缺少安全补全所需条件 |

原因出现次数合计为 112，但唯一隔离行是 111，因为同一行可能同时命中多个原因。界面和 API 分别提供 `issue_counts` 与 `quarantined_sales`，禁止把两者混为一谈。

## 质量状态口径

顶部质量百分比表示“去重后的唯一记录中，最终可用于分析的比例”：

```text
valid_sales / (raw_sales - duplicate_rows_removed)
= 11,944 / 12,055
≈ 99%
```

重复副本单独展示，不在分母中重复惩罚；隔离记录仍会降低质量百分比。抽屉完整展示原始、重复、修复、有效和隔离数量，不用单一百分比掩盖细节。

## 数据模型与追溯

- `ingestion_runs`：源文件哈希、规则版本、开始/完成时间和 JSON 摘要。
- `raw_sales`：CSV 原字段与原始行号，不参与经营聚合。
- `stores` / `products`：规范化维表。
- `sales`：只含通过规则的销售事实、整数分金额和 `amount_source`。
- `quarantined_sales`：原始行号、原始 JSON 与全部原因码。
