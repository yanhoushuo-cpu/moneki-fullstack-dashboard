# Moneki 流式问答与公开部署设计

日期：2026-08-20  
状态：已由用户批准（选择无付费 API 的方案 2）

## 1. 目标

在不要求付费大模型 API Key 的前提下，把现有门店销售看板补齐为可公开评审的交付物：

- AI 助手仍由确定性的数据库查询规划器驱动，所有数值来自 SQLite；
- 问答改为真正的 HTTP 流式响应，前端能够边接收边显示；
- 保留可选的真实模型 provider 接口，但默认部署不启用、不伪装成在线大模型；
- 创建用户账号下的公开 GitHub 仓库，并用单 Docker 镜像部署到 Render；
- 公网版本、README、自动化测试和实际行为保持一致。

## 2. 方案选择

采用“单体 Docker + FastAPI SSE + React Fetch Stream + Render 免费 Web Service”。

该方案复用现有同源生产架构，避免为 GitHub Pages 和独立 API 增加 CORS、双重部署与环境变量配置；也避免选择通常需要支付方式的部署平台。Render 免费实例可能在闲置后休眠，README 会如实说明冷启动时间。

## 3. 流式协议

新增 `POST /api/v1/chat/stream`，请求体与现有 `POST /api/v1/chat` 共用 `ChatRequest`。响应媒体类型为 `text/event-stream`，按顺序发送：

1. `start`：确认已接受请求；
2. `status`：说明正在理解问题、查询数据库或整理证据；
3. 一个或多个 `delta`：只携带新增回答文本；
4. `result`：携带完整 `ChatResponse`，包括答案、结构化证据、看板联动动作、状态和建议；
5. `done`：标记正常结束。

每个事件使用 JSON 数据，事件之间以空行分隔。服务端始终从同一个 `ChatService` 获取最终结果，再把回答按自然文本边界拆成增量，因此流式和非流式接口不会产生两个业务口径。分段是实际网络传输，不会在界面中宣称是“大模型逐 token 输出”。

错误分两类：请求校验失败仍使用标准 HTTP 4xx；开始流式后发生的异常通过 `error` 事件返回可展示消息，随后关闭连接。响应增加禁止代理缓冲与缓存的头部。

## 4. 前端交互

前端 API 层使用 `fetch`、`ReadableStream` 和流式 `TextDecoder` 解析 SSE，正确处理一个 UTF-8 中文字符或一个事件跨多个网络分片的情况。

AI 助手提交问题后立即显示处理状态和逐步增长的回答；收到 `result` 后再展示证据卡、建议与看板联动按钮。新请求会取消旧请求，组件卸载时也会中止连接。网络中断、协议不完整或服务端 `error` 事件都会进入可重试状态，并保留用户原问题。

界面明确标识当前为“数据库规则分析”，避免让评审误以为在线版本调用了真实大模型。

## 5. 部署设计

继续使用一个 Docker 镜像：构建阶段生成 React 静态文件，运行阶段由 FastAPI 同源提供 API 和前端。Docker 启动命令读取 Render 注入的 `PORT`，本地未设置时默认 `8000`；健康检查也读取相同端口。

新增 `render.yaml`，定义一个免费 Docker Web Service：

- 健康检查路径：`/api/v1/health`；
- 默认 `AI_MODE=mock`；
- SQLite 数据库在镜像构建期间从仓库 CSV 生成；
- 不配置磁盘，不依赖运行时写入的持久数据；
- 不在仓库、镜像或前端中保存任何密钥。

部署完成后用公网地址验证首页、健康检查、看板查询、数据质量和流式问答。

## 6. GitHub 发布

目标公开仓库为 `yanhoushuo-cpu/moneki-fullstack-dashboard`。保留原作业仓库为 `upstream`，将用户仓库设置为新的 `origin`，并把完成版本推送为远端 `main` 默认分支。

提交前检查变更范围和敏感信息；按“缺陷修复”“流式问答”“部署与文档”等语义拆分提交。公开 README 包含功能说明、三步本地运行、测试命令、架构、AI 边界、部署链接和 Render 冷启动说明。

## 7. 测试与验收

后端增加流式契约测试，至少验证：

- 事件顺序和 `text/event-stream` 类型正确；
- 合并所有 `delta` 后与 `result.answer` 完全一致；
- 回答、拒答、证据与看板动作都能到达最终事件；
- 流式接口与原非流式接口使用同一业务结果。

前端增加解析器与组件测试，覆盖跨字节中文分片、跨事件分片、增量显示、最终证据、错误和重试。Playwright 冒烟测试验证真实页面中的流式问答和看板联动。

最终验收必须重新运行后端测试、前端测试、类型检查、生产构建和端到端测试；部署后再通过公网健康检查和浏览器手动检查。没有对应命令的成功输出，不声明完成。

## 8. 非目标与后续扩展

本次不购买 API 额度、不要求用户提供密钥，也不把确定性规则回答描述为真实大模型生成。现有 provider 配置继续作为后续扩展点；有稳定 API Key 时，可以让 provider 参与工具选择，并沿用相同的 SSE 事件契约，而无需改动看板数据口径。
